**This MSW React tutorial mocks a real checkout and order-management API in the browser, then proves every failure mode with a Playwright end-to-end suite you can run yourself.** You'll start with no mocks at all, add [Mock Service Worker (MSW)](/tools/msw/) handlers for authentication, a paginated orders search and a checkout mutation, and finish by overriding one handler for a single test. Each step comes with the Playwright spec that checks it and a short recording of that spec running.

> **Tested with** MSW 3.0.8, @playwright/test 1.65.1 (Chromium), React 19.3.1, Vite 8.4.0 and TypeScript 7.0.2 on Node 22.23.5 (2026-11-27). All six Playwright tests pass, and the production bundle contains no MSW code. Every snippet below is copied from the sample app. devxtools.dev is independent and has no relationship with MSW or Playwright.

## What you'll build (and how MSW + Playwright fit together)

The sample is **Northwind Supply**, a small Vite + React + TypeScript order-management app with three pages: sign-in, a searchable orders table and a checkout form. The code lives in the `msw-react-checkout/` folder of the [sgedda/devxtools-tutorials](https://github.com/sgedda/devxtools-tutorials) repository.

The two tools do different jobs:

- **MSW runs inside the app.** A service worker intercepts `fetch` calls to `/api/*` and answers them from handlers in `src/mocks/handlers.ts`. The same handlers work in the dev server, in Storybook and, through `setupServer`, in Node unit tests.
- **Playwright runs outside the app.** It starts the dev servers, drives a real Chromium browser and asserts on what users see: banners, tables, disabled buttons, URLs.

Why not mock in Playwright directly? You can, and for some suites that's simpler. We cover [mocking APIs directly with Playwright `page.route`](/guides/mock-api-playwright/) in a separate guide. Here MSW owns the mocks because the handlers are part of the app: frontend developers get the same fake API in `npm run dev` that the E2E tests run against. Playwright only adds a per-test override when one test needs a different answer (Step 5). For a wider look at the library, see [how MSW compares to Nock and Polly.js](/comparisons/msw-vs-nock-vs-polly/).

| Step | What it shows | Spec |
| --- | --- | --- |

### Install MSW and its service worker

Adding MSW to your own Vite app is two commands. The second copies `mockServiceWorker.js` into `public/` and, with `--save`, records the folder in `package.json` so the worker file is updated when you upgrade MSW:

```bash
npm install --save-dev msw
npx msw init public --save
```

In the sample, that left this entry in `package.json`:

```json
"msw": {
  "workerDirectory": [
    "public"
  ]
}
```

The worker itself is one line in `src/mocks/browser.ts`:

```ts
import { setupWorker } from 'msw/browser'
import { handlers } from './handlers'

export const worker = setupWorker(...handlers)
```

### Start MSW only in development

`src/main.tsx` starts the worker before React renders, so the first request is already mocked. The guard is written inline so Vite can drop the whole branch, and with it every MSW import, from production builds:

```tsx
async function enableMocking() {
  // Checked inline (not via mockingEnabled) so production builds drop MSW entirely.
  if (!import.meta.env.DEV || import.meta.env.VITE_ENABLE_MSW === 'false') return

  const { worker } = await import('./mocks/browser')
  await worker.start({
    // Assets and Vite's own requests pass straight through; warn about API calls we forgot to mock.
    onUnhandledFrame({ frame, defaults }) {
      if (frame.protocol !== 'http') return
      const { request } = frame.data as { request: Request }
      if (new URL(request.url).pathname.startsWith('/api/')) defaults.warn()
    },
  })

  const { exposeMswBridge } = await import('./mocks/bridge')
  exposeMswBridge(worker)
}

enableMocking().then(() => {
  createRoot(document.getElementById('root')!).render(
    <StrictMode>
      <App mocked={mockingEnabled} />
    </StrictMode>,
  )
})
```

If you're coming from MSW 2: `onUnhandledRequest` is now `onUnhandledFrame`, and a custom callback receives one `{ frame, defaults }` object instead of `(request, print)`. Frames can be HTTP requests or WebSocket connections, so check `frame.protocol` before reading `frame.data.request`. A custom callback also replaces MSW's built-in skipping of static assets, which is why this one only warns for `/api/` paths.

### Set up Playwright as a real E2E suite

[Playwright](/tools/playwright/) is the test runner here, not just a screen recorder. `playwright.config.ts` starts both dev servers, keeps videos and screenshots only for failures and records a trace when a test is retried:

```ts
import { defineConfig, devices } from '@playwright/test'

const RECORDING = Boolean(process.env.RECORD_CLIPS)
const CI = Boolean(process.env.CI)

export default defineConfig({
  testDir: './e2e',
  fullyParallel: true,
  forbidOnly: CI,
  retries: CI ? 2 : 0,
  reporter: CI ? [['github'], ['html', { open: 'never' }]] : [['list'], ['html', { open: 'never' }]],

  use: {
    // The mocked dev server. Step 1 overrides this with the unmocked one.
    baseURL: 'http://localhost:5173',
    trace: 'on-first-retry',
    screenshot: 'only-on-failure',
    video: RECORDING ? { mode: 'on', size: { width: 1280, height: 720 } } : 'retain-on-failure',
    // A small delay between actions makes recordings easy to follow. Never slow down the real suite.
    launchOptions: { slowMo: RECORDING ? 200 : 0 },
  },

  projects: [
    {
      name: 'chromium',
      use: { ...devices['Desktop Chrome'], viewport: { width: 1280, height: 720 }, deviceScaleFactor: 1 },
    },
  ],

  // Playwright starts (or reuses) both dev servers before the tests and stops them afterwards.
  webServer: [
    {
      // Vite dev server with MSW intercepting /api/* in the browser.
      command: 'npm run dev',
      url: 'http://localhost:5173',
      reuseExistingServer: !CI,
    },
    {
      // Same app with VITE_ENABLE_MSW=false: /api/* goes to a backend that isn't running.
      command: 'npm run dev:unmocked',
      url: 'http://localhost:5174',
      reuseExistingServer: !CI,
      stdout: 'ignore',
      stderr: 'ignore',
    },
  ],
})
```

The specs import `test` and `expect` from `e2e/support/fixtures.ts`, which extends Playwright's `test` with a `session` option. Each spec picks which session the browser starts with (`'none'`, `'valid'`, `'expired'` or `'revoked'`) and the fixture writes it to `localStorage` before the app loads:

```ts
export const test = base.extend<Fixtures>({
  session: ['valid', { option: true }],
  // ...
})
```

## Step 1: Start with an unmocked baseline

Before mocking anything, see what the app does with no API. `.env.unmocked` sets one variable, and `npm run dev:unmocked` runs `vite --mode unmocked --port 5174`, so Vite loads it:

```bash
# `vite --mode unmocked`: same app, no MSW. /api/* is proxied to a backend that isn't running.
VITE_ENABLE_MSW=false
```

`vite.config.ts` proxies `/api` to `http://127.0.0.1:4010`, where nothing is listening, so every request fails. The app has to turn that into a clear error with a Retry button instead of an empty table. The spec points `baseURL` at the unmocked server and checks exactly that:

```ts
test.use({ baseURL: 'http://localhost:5174' })

test('shows a clear, retryable error when the orders API is unreachable', { tag: '@clip' }, async ({ page, pace }) => {
  // Real network traffic (no service worker), so Playwright can observe the failed response.
  const firstResponse = page.waitForResponse('**/api/orders?*')
  await page.goto('/orders')

  expect((await firstResponse).status()).toBeGreaterThanOrEqual(500)
  await expect(page.getByText('API: live backend')).toBeVisible()

  const error = page.getByRole('alert')
  await expect(error.getByRole('heading', { name: "Can't reach the orders API" })).toBeVisible()
  await expect(error).toContainText('attempt 1')
  await expect(page.getByRole('table')).toHaveCount(0)
  await pace(2600)

  await test.step('retry hits the network again and fails the same way', async () => {
    const retryResponse = page.waitForResponse('**/api/orders?*')
    await error.getByRole('button', { name: 'Retry' }).click()
    expect((await retryResponse).status()).toBeGreaterThanOrEqual(500)
    await expect(error).toContainText('attempt 2')
  })
  await pace(1800)
})
```

`pace()` is a fixture that waits only while recording clips. In a normal `npx playwright test` run it does nothing, so the suite stays fast.

## Step 2: Mock authenticated fetch and an expired session

Now turn MSW on. Every protected handler calls `requireAuth()`. Tokens starting with `at_live_` are valid, and tokens starting with `at_expired_` get `401 token_expired`:

```ts
function requireAuth(request: Request) {
  const token = request.headers.get('Authorization')?.replace(/^Bearer /, '')
  if (!token) {
    return errorResponse(401, { error: 'unauthorized', message: 'Sign in to continue.' })
  }
  if (token.startsWith('at_expired_')) {
    return errorResponse(401, { error: 'token_expired', message: 'Your access token has expired.' })
  }
  return null
}
```

The refresh endpoint swaps a refresh token for new tokens after 1.5 seconds, or returns `401` for a revoked one:

```ts
http.post('/api/auth/refresh', async ({ request }) => {
  const { refreshToken } = (await request.json()) as { refreshToken: string }
  await delay(1500) // token refresh is a separate round-trip, keep it visible
  if (!refreshToken?.startsWith('rt_') || refreshToken === 'rt_revoked') {
    return errorResponse(401, { error: 'refresh_token_invalid', message: 'Please sign in again.' })
  }
  return HttpResponse.json({
    accessToken: `at_live_${crypto.randomUUID().slice(0, 8)}`,
    refreshToken: `rt_${crypto.randomUUID().slice(0, 8)}`,
    user: demoUser,
  })
}),
```

On the app side, `apiFetch()` in `src/api/client.ts` refreshes once on `token_expired` and replays the original request. If the refresh fails, it clears the session and the app redirects to sign-in:

```ts
export async function apiFetch<T>(path: string, init: RequestInit = {}): Promise<T> {
  const session = loadSession()
  let response = await send(path, init, session)

  if (response.status === 401 && session) {
    const error = await parseError(response.clone())
    if (error.code === 'token_expired') {
      const refreshed = await refreshSession(session)
      response = await send(path, init, refreshed)
    }
  }

  if (!response.ok) throw await parseError(response)
  return (await response.json()) as T
}
```

The spec has two tests. The first starts with an expired access token and checks that the session renews silently. The second starts with a revoked refresh token and checks the redirect to sign-in:

```ts
test.describe('expired access token', () => {
  test.use({ session: 'expired' })

  test('renews the session silently and loads the orders', { tag: '@clip' }, async ({ page, pace }) => {
    await page.goto('/orders')
    await pace(600)

    const banner = page.getByRole('status')
    await expect(banner).toHaveText('Session expired (401). Renewing your access token…')
    await expect(banner).toHaveText('Session renewed. You are still signed in.')

    await expect(page.getByRole('row', { name: /NW-10423/ })).toBeVisible()
    await expect(page.getByTestId('signed-in-user')).toHaveText('Maya Chen')
    // ...also checks the stored token now starts with at_live_, and that the next page needs no refresh
  })
})

test.describe('revoked refresh token', () => {
  test.use({ session: 'revoked' })

  test('redirects to sign-in and returns to the orders afterwards', async ({ page }) => {
    await page.goto('/orders')

    await expect(page).toHaveURL(/\/sign-in\?reason=expired/)
    await expect(page.getByRole('alert')).toContainText('Your session has ended')

    await page.getByLabel('Password').fill('correct-horse-battery')
    await page.getByRole('button', { name: 'Sign in' }).click()

    await expect(page).toHaveURL(/\/orders/)
    await expect(page.getByRole('row', { name: /NW-10423/ })).toBeVisible()
  })
})
```

## Step 3: Mock paginated search with loading and empty states

`GET /api/orders?q=&status=&page=` filters and paginates 23 deterministic orders, six per page. Every response waits `delay(650)` first, so the loading skeleton is visible the way it would be on a real network:

```ts
// GET /api/orders?q=&status=&page=
http.get('/api/orders', async ({ request }) => {
  const unauthorized = requireAuth(request)
  if (unauthorized) return unauthorized

  const url = new URL(request.url)
  const q = (url.searchParams.get('q') ?? '').trim().toLowerCase()
  const status = (url.searchParams.get('status') ?? 'all') as OrderStatus | 'all'
  const page = Math.max(1, Number(url.searchParams.get('page') ?? '1'))

  await delay(API_LATENCY_MS)

  const matches = orders.filter(
    (order) =>
      (status === 'all' || order.status === status) &&
      (!q || [order.id, order.customer, order.email].some((field) => field.toLowerCase().includes(q))),
  )
  const totalPages = Math.max(1, Math.ceil(matches.length / PAGE_SIZE))
  return HttpResponse.json({
    orders: matches.slice((page - 1) * PAGE_SIZE, page * PAGE_SIZE),
    page,
    pageSize: PAGE_SIZE,
    total: matches.length,
    totalPages,
  })
}),
```

Because the data is fixed, the spec can assert exact counts at each step: paginate, filter by status, search, and hit the empty state:


## Step 4: Mock a checkout error and test inline recovery

Mutations need failure tests too. The default `POST /api/checkout` handler treats the test card ending in `0119` as a payment-provider timeout. The first attempt gets a `500`, and a retry with the same idempotency key succeeds:

```ts
http.post('/api/checkout', async ({ request }) => {
  const unauthorized = requireAuth(request)
  if (unauthorized) return unauthorized

  const body = (await request.json()) as CheckoutRequest
  await delay(900)

  if (body.payment.last4 === TRANSIENT_FAILURE_CARD_LAST4 && !failedOnce.has(body.idempotencyKey)) {
    failedOnce.add(body.idempotencyKey)
    return errorResponse(500, {
      error: 'payment_provider_timeout',
      message: 'The payment provider timed out before confirming the charge.',
    })
  }

  for (const item of body.items) {
    if ((inventory[item.sku] ?? 0) < item.quantity) {
      return errorResponse(409, {
        error: 'out_of_stock',
        message: 'An item in your cart is no longer available.',
        sku: item.sku,
        available: inventory[item.sku] ?? 0,
      })
    }
  }
  // ...otherwise 201 with an order ID, total and estimated delivery
}),
```

The checkout page creates one idempotency key per cart, so pressing **Try again** can't charge twice. The spec checks that the error is shown inline, that the cart and form survive it, and that the retry confirms the order:

```ts
test('recovers from a 500 at checkout without losing the cart', { tag: '@clip' }, async ({ page, pace }) => {
  await page.goto('/checkout')
  await expect(page.getByRole('heading', { name: 'Checkout' })).toBeVisible()

  await fillShippingAndPayment(page, '4000 0000 0000 0119')
  await pace(400)

  const placeOrder = page.getByRole('button', { name: /Place order/ })
  await placeOrder.click()
  await expect(page.getByRole('button', { name: 'Placing order…' })).toBeDisabled()

  const banner = page.getByTestId('checkout-error')
  await expect(banner).toContainText("We couldn't confirm your payment")
  await expect(banner).toContainText('HTTP 500 · payment_provider_timeout')

  await test.step('cart and form state survive the error', async () => {
    await expect(page.getByLabel('Street address')).toHaveValue('Sveavägen 44')
    await expect(page.getByLabel('Card number')).toHaveValue('4000 0000 0000 0119')
    await expect(page.getByRole('list', { name: 'Cart' }).getByRole('listitem')).toHaveCount(3)
    await expect(page.getByTestId('order-total')).toHaveText('$568.00')
  })
  await pace(2600)

  await banner.getByRole('button', { name: 'Try again' }).click()
  const confirmation = page.getByTestId('order-confirmation')
  await expect(confirmation.getByRole('heading')).toHaveText(/Order NW-\d+ confirmed/)
  await expect(confirmation).toContainText('4 items · $568.00')
  await pace(1200)
})
```

## Step 5: Override a handler for one test with worker.use()

Some states only matter to one test, like an item selling out between page load and checkout. Changing `handlers.ts` for that would affect every test. Instead, `src/mocks/bridge.ts` exposes the running worker on `window.msw`, and only when MSW is running on the dev server:

```ts
export function exposeMswBridge(worker: SetupWorker): void {
  window.msw = { worker, http, HttpResponse, delay }
}
```

Playwright can't import the worker, because the worker lives in the browser. So the spec waits for `window.msw` and calls `worker.use()` inside `page.evaluate()`. The runtime handler is prepended. It returns `409` only when the cart contains the sold-out SKU, and otherwise returns nothing, so MSW falls through to the default handler:

```ts
const SOLD_OUT_SKU = 'NW-HDPHN-02'

test('shows out-of-stock recovery when checkout returns 409 for one SKU', { tag: '@clip' }, async ({ page, pace }) => {
  await page.goto('/checkout')
  await waitForMockWorker(page)

  // This callback runs in the browser, where the app exposed the worker on window.msw.
  await page.evaluate((sku) => {
    const { worker, http, HttpResponse } = window.msw!
    worker.use(
      http.post('/api/checkout', async ({ request }) => {
        const body = (await request.clone().json()) as CheckoutRequest
        // No sold-out item in this cart? Return nothing and MSW falls through to the default handler.
        if (!body.items.some((item) => item.sku === sku)) return
        return HttpResponse.json(
          { error: 'out_of_stock', message: 'An item in your cart is no longer available.', sku, available: 0 },
          { status: 409 },
        )
      }),
    )
  }, SOLD_OUT_SKU)

  await fillShippingAndPayment(page, '4242 4242 4242 4242')
  await page.getByRole('button', { name: /Place order/ }).click()

  const banner = page.getByTestId('out-of-stock')
  await expect(banner).toContainText('Noise-cancelling headphones just sold out')
  const soldOutLine = page.getByRole('listitem').filter({ hasText: SOLD_OUT_SKU })
  await expect(soldOutLine).toContainText('Out of stock')
  await expect(page.getByRole('button', { name: /Place order/ })).toBeDisabled()
  await pace(2400)

  await banner.getByRole('button', { name: 'Remove item' }).click()
  await expect(soldOutLine).toHaveCount(0)
  await expect(page.getByTestId('order-total')).toHaveText('$319.00')
  await pace(1000)

  // The cart no longer contains the SKU, so this request falls through to the default handler.
  await page.getByRole('button', { name: 'Place order · $319.00' }).click()
  const confirmation = page.getByTestId('order-confirmation')
  await expect(confirmation.getByRole('heading')).toHaveText(/Order NW-\d+ confirmed/)
  await expect(confirmation).toContainText('3 items · $319.00')
  await pace(400)
})
```

`waitForMockWorker()` is a helper in the fixtures file. It waits until `window.msw !== undefined`. `worker.use()` never changes `src/mocks/handlers.ts`, and every Playwright test gets a fresh page, so the override can't leak into the next test.

## Running the suite in CI (and debugging with recordings)

The config already behaves differently when `CI` is set: `forbidOnly` fails the run if someone left a `test.only` in a spec, failed tests get two retries, and the reporters switch to GitHub annotations plus an HTML report. Playwright also starts fresh dev servers instead of reusing existing ones. The CI job itself only needs these commands (Playwright runs Chromium headless by default):

```bash
npm ci
npx playwright install --with-deps chromium
CI=true npx playwright test
```

Upload `playwright-report/` and `test-results/` as build artifacts. When a test fails:

- **Videos and screenshots** are kept only for failed tests (`video: 'retain-on-failure'`, `screenshot: 'only-on-failure'`).
- **Traces** are recorded on the first retry (`trace: 'on-first-retry'`). Open one with `npx playwright show-trace <path-to-trace.zip>`, or open the HTML report with `npx playwright show-report` and click into the test.
- **Locally**, `npm run test:e2e:ui` opens Playwright's UI mode, where you can step through each action and watch the DOM.

The clips on this page come from the same specs. `npm run record:clips` sets `RECORD_CLIPS=1`, which turns on 1280×720 video and a 200 ms `slowMo` and makes `pace()` wait. Tests tagged `@clip` save their video, and `scripts/encode-clips.sh` encodes MP4, WebM and a WebP poster with ffmpeg. A normal test run is never slowed down.

### Keep MSW out of the production bundle

The inline `import.meta.env.DEV` check in `main.tsx` means Vite removes the dynamic imports of `./mocks/browser` and `./mocks/bridge` from production builds. To check, build and search the JavaScript output:

```bash
npm run build
grep -c "setupWorker\|mockServiceWorker\|HttpResponse" dist/assets/*.js   # prints 0
```

On our build it printed `0`. Vite still copies `public/mockServiceWorker.js` into `dist/`, because everything in `public/` is copied. Production code never registers it, but you can delete it after the build if you'd rather not deploy the file.

## FAQ

### Should I mock APIs with MSW or Playwright page.route?

Use MSW when the mocks should live with the app and be reused in development, Storybook and unit tests. Use `page.route` when only the E2E suite needs them, or when you can't change the app. Many teams combine them, as this tutorial does in Step 5. Our guide to [mocking APIs directly with Playwright `page.route`](/guides/mock-api-playwright/) covers that approach, including HAR replay.

### Does MSW's service worker work in headless Playwright CI runs?

Yes. This suite runs in headless Chromium, and all six tests pass. Service workers need a secure context, and `http://localhost` counts as one. Don't set Playwright's `serviceWorkers: 'block'` option for these tests, because that stops MSW from registering. We only tested Chromium for this tutorial.

### How do I override MSW handlers per Playwright test without leaking state?

Expose the worker on `window` in development only, then call `worker.use()` inside `page.evaluate()`, as in Step 5. Runtime handlers belong to the page they were added in, and Playwright gives every test a fresh browser context, so nothing carries over. To reset within one test, call `worker.resetHandlers()` the same way.

### How do I make sure MSW isn't bundled into production?

Start the worker behind an inline `import.meta.env.DEV` check and load MSW with dynamic `import()`, so the bundler can drop it. Then verify it: build, and search `dist/assets/` for MSW identifiers such as `setupWorker`. The `mockServiceWorker.js` file in `public/` is still copied to `dist/`, but nothing registers it.

### Can I reuse the same MSW handlers in Jest or Vitest unit tests?

Yes. Handlers are plain request/response functions. Pass the same `handlers` array to `setupServer` from `msw/node` in your test setup. Note that MSW 3 is ESM-only and needs Node 22 or later. See [how to mock API calls in Jest](/guides/mock-api-calls-jest/) for the setup.
